## 1. drumCover 操作介面：扒譜、預覽、編輯版本、輸出（規劃定案，2026-11-07；**第一版已實作**，tickets #2–#10）

> 實作狀態：第一版範圍內的功能已完成（`tools/editor/`，啟動用根目錄的 `啟動操作介面.bat`），測試在 `tests/`。
> 下面的規劃保留當時的決策脈絡；與現況不同之處已就地標註。「第二版」項目與草稿 API 表中的舊端點仍是未做／已作廢。

### 動機

AI 自動扒譜在 KICK BACK 驗證的準確度約 95.6%（完全正確的小節 54.9%）。剩下的落差光靠音訊推不出來，
例如譜上省略的輕音、開/閉 hi-hat、重音，要做到「跟原譜一模一樣」需要人工修正。
使用者的鼓樂知識不多，所以介面要能**用耳朵比對**，而不只是看譜。
使用者也想對同一首歌保留**好幾份自己的鼓譜**（例如照原譜版、練習用簡化版），各自輸出。

用語見 [GLOSSARY.md](../GLOSSARY.md)（專案、鼓譜、AI 譜、舊 AI 譜、編輯版本、來源版本、練習影片、鼓譜圖檔、輸出）；
為什麼用本機網頁見 [ADR 0001](adr/0001-本機網頁應用程式.md)。

### 定案的規劃（2026-11-07 拷問結果）

**架構**
- 本機網頁：Python 伺服器只綁 `127.0.0.1:8765`，只給這台電腦用。根目錄放 `啟動操作介面.bat`（已實作），雙擊用 venv 啟動伺服器並自動開瀏覽器；
  關掉命令列視窗就結束。`.claude/launch.json` 加一個設定，供 Browser pane 測試
- 沿用 `tools/editor/` 草稿繼續做（下面「草稿既有設計」）
- **不經過 Claude**：直接呼叫 `drumcover.py` 的 download → analyze → score；skill 的臨場判斷（剪片頭、裁切位置）改成畫面上的選項。
  `drum-score-video` skill 要補一段「也可以用 app」

**鼓譜與版本**
- `projects/<歌>/score.json` = **AI 譜**，唯讀，扒譜流程不用改
- **編輯版本**：`projects/<歌>/versions/<id>.json`，檔內記 `name`（版本名稱）、`from`（來源版本）、建立時間。
  可以從**任何**鼓譜（AI 譜、舊 AI 譜、其他編輯版本）複製出來
- 存檔直接覆蓋該版本，不留存檔歷史；復原/重做只在當次編輯中有效
- 在 AI 譜（或舊 AI 譜）上點格子 → 先跳「命名新版本」對話框，複製成新版本後再套用這次修改
- 切換版本時有未存修改 → 問「存檔後切換／放棄修改／取消」
- 編輯版本可以改名、刪除（刪除前確認）；AI 譜不能改名或刪除
- 來源版本被刪 → 只是記錄資訊，那些版本照常可用，顯示「來源已刪除」；「還原成來源版本」改成還原成 AI 譜
- **重新扒譜**：舊的 AI 譜自動保存成唯讀的**舊 AI 譜**，再產生新的 AI 譜；編輯版本完全不動。
  新舊 AI 譜的小節時間對不上（某小節 `t0` 差 >0.1 秒）時，在相關編輯版本上顯示警告
- 草稿原本的 `score.auto.json` 備份、直接改 `score.json` 的做法**作廢**，改用上面的版本機制。
  （2026-11-07 確認現有專案都沒有 `score.auto.json` 或 `versions/`，不用搬移）

**畫面流程**
1. 首頁：專案清單＋「新增專案」
   - 輸入來源：YouTube 網址或本機 mp4 路徑
   - 專案名稱：預設用 YouTube 影片標題，可改，允許中文
   - 進階選項（預設收起）：片段開始秒數與長度（`--start` / `--dur`，剪片頭用）、扒譜音源（`--source`）
   - 畫面裁切位置（`--crop-y`）不在這裡選，輸出練習影片時才選
2. 長時間工作（下載、扒譜、輸出練習影片）：**同時只跑一個**，跑的時候不能再送出新的；
   顯示目前步驟（下載 → 分離鼓聲 → 扒譜 → 排版 / 輸出）；關掉分頁不中斷，重開看得到進度；失敗顯示錯誤，可從失敗那步重試。
   工作進行中仍可編輯、預覽、存檔任何專案
3. 編輯畫面：上方「版本選單＋影片＋**即時**鼓譜游標預覽」（瀏覽器裡邊播邊畫目前這一行和游標，不用 render，
   切版本或改譜馬上看到）；下方方格編輯器

**輸出**
- 輸出位置：`projects/<歌>/exports/`，檔名用版本名稱（例如 `簡化版.mp4`、`簡化版.pdf`），同一版本再輸出就**覆蓋**；
  畫面有「開啟輸出資料夾」按鈕
- **練習影片**：輸出時選畫面裁切位置、要不要用 % 記號；用的是**按下輸出那一刻的鼓譜快照**；走長時間工作佇列。
  `drumcover.py render` 要加 `--score <檔案>`（指定用哪份鼓譜）和 `--out`
- **鼓譜圖檔**：A4 直式、每行 4 小節、第一頁上方有歌名＋版本名稱＋BPM、% 記號可選；
  PDF（多頁一檔）或 PNG（每頁一張）。幾秒內完成，不排隊。`notation.py` 要新增整頁排版（目前只有 `render_line`）

**第一版範圍**
- 做：小節總覽與跳轉、方格編輯（含三連音）、即時鼓譜預覽、原曲播放（慢速、單一小節循環）、復原/重做、
  同上一小節、複製/貼上、還原成來源版本、**合成鼓聲疊原曲一起聽**
- 第二版：AI 信心底色與橘點不一致提示、只播分離後的鼓聲（drums.wav）
- 不做：在 app 裡刪除或改名**專案**（會連影片和分析檔一起刪，風險高、用到少；要做時直接處理資料夾）

### 後端 API（server.py）

> 下表是**草稿時期**的端點，已過時：`score.auto.json` 備份與 `/api/auto_bar` 已作廢（改用版本機制：`/api/versions`、
> `/api/score?v=`、`/api/projects/*`、`/api/job` 等），`/api/render`、`/api/render_status` 也改成走長時間工作佇列。
> 現行端點以 `tools/editor/server.py` 為準。

| 方法 | 路徑 | 用途 |
|---|---|---|
| GET | `/api/projects` | 列出有 score.json 的專案 |
| GET | `/api/score?p=` | 回傳 score、每小節每格的 AI 信心（`act`）、可用的媒體檔 |
| POST | `/api/score?p=` | 存檔：重算每個事件的 `t`、`idx`；**第一次存檔前把原檔備份成 `score.auto.json`** |
| GET | `/api/auto_bar?p=&i=` | 取 AI 原始版本的某一小節（「還原為 AI 版本」用） |
| POST | `/api/line` | 傳入 4 個小節 → 回傳排版好的譜面 PNG（base64），目前小節用淡黃色標示 |
| POST | `/api/preview_line` | 傳入（可含未存檔修改的）整份鼓譜與行號 → 回傳該行譜面 PNG、游標位置 `[t, x]`、小節 x 範圍、每行時間範圍；前端依影片時間畫游標（即時預覽） |
| GET | `/media/<p>/<file>` | video.mp4 / mix.wav / drums.wav，**要支援 HTTP Range**（影片拖曳、跳播需要） |
| POST | `/api/render?p=` | 背景執行 `drumcover.py render`（參數：crop_y、simile） |
| GET | `/api/render_status?p=` | 輸出進度（解析 ffmpeg 的 `time=`） |

AI 信心的算法：用 `drumcover.load_activations(P, "hybrid")`，先套用 `score["offset_ms"]`，
在每個 16 分格取 ±1/8 拍視窗內的最大機率，三連音格取 ±1/6 拍。
編輯器的樂器列對到 ADTOF 類別：CR/RD→CY、HH/HO→HH、SD/XS→SD、TH/TM/TF→TM、BD→BD、HF→無。

### 前端功能（index.html）

- **小節總覽**：所有小節排成小方塊，每 4 個一組（一行）。顏色：AI 有點不確定（淺橘）、很不確定（深橘，≥3 處）、
  整小節休止（灰）、已修改（綠框）、目前小節（藍框）。點一下就跳過去。
- **譜面預覽**：顯示目前這一行（4 小節），由後端用 `notation.py` 即時排版，所見即所得；點譜面上的小節可跳轉。
- **方格編輯**：
  - 列 = 樂器，順序照五線譜由上到下：Crash ⊗、Ride、Hi-hat 閉、Hi-hat 開、高/中音 Tom、小鼓、Cross-stick ▲、落地 Tom、大鼓、Hi-hat 踏
  - 欄 = 每拍 4 格（16 分音符）；每拍上方有「3」按鈕可切換成三連音（3 格）。切換時音符就近對應：16 分 e→T2、&→T2、a→T3，反向 T2→e、T3→a
  - 點格子新增/刪除音符；hi-hat 開與閉在同一格互斥
  - 格子底色深淺＝AI 信心；**橘點＝不一致**（有寫音但 AI 信心 <0.3，或沒寫音但 AI 信心 ≥0.2，且同類別的其他樂器也沒寫在這格）
  - 每小節「不確定度」＝橘點數，用來給總覽上色
- **小節工具**：同上一小節、複製/貼上、清空、還原為 AI 版本、復原/重做（逐小節快照，最多 300 步）
- **試聽**：
  - 音源：原曲（用 `<video>` 播放，同時看得到鼓手畫面）或分離後的鼓聲（`<audio>` 播 drums.wav，影片靜音同步）
  - 速度 100/75/50%，`preservesPitch = true`（慢速不變調）
  - 模式：只聽音源／音源＋合成鼓聲／只聽合成鼓聲。**合成鼓聲＝用 WebAudio 把「目前寫的譜」即時合成出來**，
    跟原曲疊在一起聽，對不上的地方就是要改的地方
  - 同步做法：requestAnimationFrame 偵測媒體時間第一次前進的畫格，記下 (AudioContext 時間, 媒體時間) 對應，
    再把這小節的音排程到 `ctx.currentTime + (t - media) / rate`
  - 可循環、可「提前一拍開始」；方格上有紅色播放頭（依實際拍點分段對應）
  - 合成音色：BD 正弦波 140→45Hz、SD 帶通噪音 1.9kHz＋三角波、HH 高通噪音 7.5kHz 短衰減、HO 長衰減、
    CR 高通噪音 1.3 秒、RD 帶通噪音＋3kHz 正弦、Tom 正弦下滑（TH 260、TM 180、TF 115Hz）、XS 1.15kHz 三角波短音
- **輸出影片**：選上方畫面裁切位置、要不要用 % 記號，按下後先存檔再輸出，顯示進度
- **快捷鍵**：←/→ 換小節、空白鍵播放、L 循環、Ctrl+Z/Y、Ctrl+C/V、Ctrl+S；有未存修改時關頁面會提醒

## 2. 另外指定高音質音訊檔來扒譜（擱置中，2026-10-05）

### 動機

YouTube 下載的音訊只有約 128kbps AAC，高頻細節（hi-hat、銅鈸、輕音）損失最多。
使用者如果手上有同一首歌的無損音檔（WAV / FLAC）或鼓的分軌，用它來扒譜會更準；影片畫面照用原本的。

### 規劃的做法

- `drumcover.py` 的 `download` / `analyze` 加參數 `--audio <檔案>`：
  - 用 ffmpeg 把它轉成 `projects/<name>/mix.wav`（44.1kHz 立體聲），取代從影片抽出來的音訊
  - 加 `--drums-stem <檔案>`：有鼓的分軌時直接當成 `drums.wav`，跳過 Demucs
- **時間對齊**（必要）：外部音檔跟影片的起點通常不一樣。用影片音訊與外部音檔的 onset envelope 做互相關（cross-correlation），
  算出偏移秒數，存在 `projects/<name>/audio_offset.json`；扒譜在外部音檔的時間軸上做，`render` 時把所有事件時間加上偏移。
  要檢查互相關峰值是否夠明顯，不明顯就警告並請使用者手動給 `--audio-offset`
- 外部音檔取樣率不同、或速度有微小差異（例如不同版本的母帶）時，互相關只對齊起點；
  若需要的話，可以分段計算偏移，檢查有沒有漂移
- 成品影片的聲音維持用影片原本的音訊（跟畫面同步），只有扒譜改用外部音檔
- 加進 `drum-score-video` skill 的步驟說明

## 4. 收集更多附譜影片來驗證（等使用者提供影片，2026-10-05）

### 動機

目前所有門檻只用 KICK BACK 一首調出來，有過擬合風險；開/閉 hi-hat、重音、輕音也沒有足夠的標準答案可驗證。
**使用者之後會提供其他不同曲風的附譜影片**，收到時照下面的標準挑選、處理。

### 討論結論（輕音 / 開閉 hi-hat / 重音）

| 項目 | 模型現在聽得到嗎 | 真正的瓶頸 | 調整音訊有沒有用 |
|---|---|---|---|
| 譜上省略的輕音 | 聽得到（就是「多抓」的來源） | 判斷**要不要寫**：要量每一下的相對音量＋記譜慣例 | 幾乎沒用；壓縮/音量平均化反而有害 |
| 開/閉 hi-hat | ADTOF 只有一個 HH 類別 | **分類**：看餘音長度 | 有用：分離出單獨 hi-hat 音軌或濾高頻段再量 |
| 重音 | 模型不輸出音量 | 量相對音量＋記譜慣例 | 有限 |

KICK BACK 的數據：
- 多抓 95 個（HH 62、SD 17），大多在 16 分的 e/a 位置 → 輕音或伴奏漏音的特徵。
  做法：用 drums.wav 量音量，跟同小節同樂器比；HH 若完整混音有、鼓聲音軌沒有，多半是伴奏漏音。
  理論上限：多抓全去掉、漏抓不變，F1 95.6% → 約 98.5%。
- 標準答案有約 35 個開 hi-hat（第 24、39、41、57～64 小節），但 `evaluate.py` 的 `CATEGORY` 把 HO 併進 HH，
  **目前 hi-hat 94.4% 沒有檢查開閉**。第 57、61 小節 crash 與開 hi-hat 同時出現，crash 餘音會干擾。
- 原譜的 hi-hat 重音 `>` 只出現在前奏第 1～8 小節（只有 hi-hat 的段落），其他段落的 `>` 都在 crash 上。
  目前 auto 不會出現 hi-hat 重音（`notation.py` 的 `ACCENTED` 只有 CR），`gt.txt` 也沒有重音欄位。
  要驗證時：先在 `gt.txt` 補重音標記（格式要擴充），前奏只有 hi-hat、沒有其他鼓干擾，適合當重音偵測的第一個測試段，
  但樣本只有 8 小節。
- 音訊處理：無損音源（見第 2 項）、細分鼓組的分離模型（例如 LarsNet，可分出單獨 hi-hat）、濾頻段算特徵 → 有用；
  把 EQ 過的音訊直接餵 ADTOF、壓縮、放慢 → 沒用或有害。

### 挑選影片的標準

- **譜要清楚、完整**：整首都有譜，可逐小節手抄（最好跟 KICK BACK 一樣逐行顯示的鼓譜影片）
- 依目的挑：
  - 開/閉 hi-hat：開 hi-hat 很多的歌（disco 反拍開 hi-hat、搖滾副歌每拍開）
  - 重音：原譜有在 hi-hat / 小鼓上標 `>` 的
  - 輕音：原譜**有寫**輕音的（括號，funk / R&B 常見）和**省略**的都要
  - 整體：不同速度、曲風，錄音室版與現場版
- 鼓手翻打影片的鼓聲通常比原曲清楚、比較好扒，要混一兩支「原曲音訊＋鼓譜」的，成績才不會偏高
- 目標 3～5 首。**留一首完全不調參數、最後才拿來驗收**，其他首用來調整

## 5. 固定 Demucs 的亂數種子，讓重跑結果完全相同（擱置中，2026-10-05）

### 現象

day6-happy 從頭重跑 `analyze` 後，126 小節中有 13 小節不同（每小節差 1~2 個音，多為 crash/ride、tom、小鼓），
小節線與拍點完全相同。原因：Demucs 預設 `--shifts 1`，`demucs/apply.py` 用 `random.randint(0, max_shift)`
隨機挑 0~0.5 秒的位移、沒有固定種子 → 每次 `drums.wav` 略不同（差異約 -25dB）→ `act_drums.npy` 跟著變 →
門檻邊緣的音進出。`mix.wav`、`act_mix.npy`、`beats.json` 重跑完全相同（ADTOF、beat_this 沒有隨機性）。

### 影響

- 拿來練習：影響很小，變動的都是模型本來就不確定的音
- **驗證準確度時**：比較改程式前後的分數要沿用同一份分析檔，不要重跑 `analyze`，否則分數會混進隨機差異

### 規劃的做法

- `cmd_analyze` 呼叫 Demucs 前固定種子（例如改成在 Python 內呼叫 `demucs.separate.main` 前 `random.seed(0)`、
  `torch.manual_seed(0)`），品質不變、結果可重現
- 其他選項：`--shifts 0`（不位移，品質可能稍降）、`--shifts 5~10`（更穩定但仍有隨機、慢數倍）
- 做完要同一首跑兩次比對 `drums.wav` 是否完全相同（GPU 運算本身可能有極微小不確定性）

## 6. 操作介面第一版之後暫不處理的項目（擱置中，2026-11-08）

操作介面第一版（#2–#10）做完後，兩輪 code-review 留下的項目。都不影響第一版使用。

### `DRUMCOVER_CODEC` 預設是 `h264_nvenc`

沒有 NVIDIA 顯卡的電腦輸出練習影片會失敗，目前要自己設環境變數 `DRUMCOVER_CODEC=libx264`。
規劃的做法：`render` 先偵測 `h264_nvenc` 能不能用（例如 ffmpeg 試編一幀），不能用就退回 `libx264`，並印出退回的訊息。

### 伺服器重啟後，失敗專案的重試資訊會消失

失敗的是哪一步（`failed_step`）和重新扒譜的步驟（`last_reimport`）只存在伺服器記憶體。重啟後只能從第 0 步重試；扒譜的中間檔存在時各步會自己跳過，所以不會白跑，但重新扒譜的重試入口會消失。
規劃的做法：失敗時把種類、步驟、錯誤寫進專案資料夾的小檔（例如 `job_failed.json`），啟動時讀回來；成功時刪掉。

### 對齊警告的判斷

- 對來源是 AI 譜的版本，用「建立時間 <= 取代時間」推斷它根據哪份舊 AI 譜。連續重新扒譜多次、或時間格式不一致時可能誤判。
- 新舊 AI 譜小節數不同也算對不齊，但 spec 只說「某小節起點差超過 0.1 秒」。
規劃的做法：版本建立時就把「根據哪一份 AI 譜」的 id 記進檔內中繼資料，不要事後推斷。小節數不同是否要警告，先問使用者。

### 版本種類與 id 混用同一個字串

`"ai"` 同時是版本 id 也是種類，`vid == AI`、`meta.kind` 的判斷散在 `list_versions`、`require_editable`、`derived_old_ai`、`restore_bar`。
規劃的做法：版本資料用一個小型別（id、種類、是否唯讀）包起來，各處問它而不是比字串。

### `server.py` 太長

約 670 行，同時含路由、專案命名驗證、版本管理、預覽繪圖、重新扒譜邏輯；多張票並行時 `server.py` 和 `index.html` 合併衝突最多。
規劃的做法：依責任拆成路由、版本、專案、預覽四個模組；測試只走 HTTP，拆檔時不用改。`index.html` 維持單一檔案。
